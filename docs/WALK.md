# 순회(walk) 설계 초안

> 상태: **설계 초안, 구현 없음.** 이 문서가 확정되면 구현한다. 숫자(상한 등)는 초안 값이고 `measure`로 조정한다.
> 관련 문서: `docs/COMMANDS.md`(명령 표, 역할, 정책), `docs/IR.md`(중간 표현).

## 1. 목적

PKGBUILD와 `.install`을 **실행하지 않고**, 실행되는 순서대로 따라가며 "무엇이 일어날 수 있는가"를 모은다.
지금은 구문 트리의 명령을 줄 순서대로 훑고(`astadapt.steps`), 함수의 역할은 호출 그래프로 따로 계산한다(`roles.py`).
이 문서는 둘을 하나의 **상태를 갱신하는 순회**로 합친다. 이유는 다음과 같다.

- `alias`와 함수 정의는 **그 줄 이후에만** 효력이 있고, 조건문 안에 있을 수도 있다. 미리 전처리할 수 없다.
- 상대 경로를 풀려면 `cd`의 순서를 따라가야 한다.
- 변수 값, `set -e`, `shopt expand_aliases`도 순서와 조건에 의존한다.
- 분석이 틀릴 때는 **경고를 놓치는 쪽이 아니라 더 많이 내는 쪽**으로 틀려야 한다(may 분석, 5절).

## 2. 전체 흐름

| 단계 | 하는 일 | 지금 코드 |
|---|---|---|
| 0 입력 수집 | PKGBUILD, 같은 저장소의 다른 파일, 이전 버전 차이 | `fetch.py`, `corpus.py` (일부) |
| 1 구문 분석 | 파일을 구문 트리로. 순서와 무관한 문법 정리(따옴표 이어 붙이기, `$'..'`) | `preprocess.py`, `shast.py`, `parsed.py` |
| 2 **순회** | 시간선별로 실행 순서대로 걷는다. 상태를 갱신하고, alias와 함수를 풀고, 함수를 인라인하고, 난독화를 풀고, 분기와 반복을 처리한다 | 없음 (이 문서) |
| 3 데이터 흐름 | 파이프, 리다이렉션, `$(...)`, 임시 파일로 단계들을 잇는다 | `fetch-then-execute` 일부 |
| 4 표 조회 | 각 단계를 명령 표로 번역해 (동작, 위치, 하위 분류) 태그를 붙인다. 예상 행동을 기록한다 (IR) | `commandtable.py`, `strict.py`, `ir.py` |
| 5 정책 | 역할 × 칸에 하위 분류 예외를 적용해 판정한다 | `strict.classify` |
| 6 보고 | 보고서와 **분석하지 못한 것**을 stdout으로 | `report.py`, `cli.py` |
| 7 사용자 결정 | `[y/N]` (경고면 `yes` 입력). 분석 실패 시 안전 쪽(N)으로 닫는다 | `cli.py` |

이 문서는 2단계를 정의한다. 나머지는 2단계의 출력 형식(10절)만 맞추면 따로 다룰 수 있다.

## 3. 값과 상태

### 3.1 값 (격자)

모든 값(변수, 인자, 명령 이름, 경로)은 세 가지 중 하나다. 위로 올라갈수록 덜 안다.

```
unknown            맨 위. 무엇이든 될 수 있다
 └ set {a, b, ...} 작은 집합 (크기 ≤ SET_MAX, 초안 8). 둘 이상의 값 중 하나
    └ known "s"    알려진 문자열
```

- **합류(join)**: 같은 값이면 유지, 다르면 둘의 합집합(집합), 집합이 `SET_MAX`를 넘으면 `unknown`.
- 값에서 파생된 값(연결, 치환, 슬라이스)은 입력이 모두 known이면 known, 일부가 set이면 가능한 조합의 set(상한 안에서), 하나라도 unknown이면 unknown. 이것이 **오염(taint) 전파**다.
- 글롭(`*.txt`), 명령 치환 `$(...)`, `read`, 환경 변수(`CARCH`)는 unknown이다. 단 아는 정보는 남긴다. 예를 들어 `$srcdir/*.txt`는 "빌드트리 안의 경로"라는 위치 정보를 유지한다.
- 이후 확장: 접두어/접미어를 유지하는 문자열 영역(`${a}rl`의 `rl`).

### 3.2 상태

순회는 다음 상태를 들고 간다.

| 항목 | 내용 |
|---|---|
| 변수 | 이름 → 값 (3.1). 배열은 원소별 |
| alias | 이름 → 대체 문자열. `shopt -s expand_aliases`가 켜진 뒤에만 효력 |
| 함수 | 이름 → 정의 (재정의되면 마지막 것). 호출 시점의 정의를 쓴다 |
| 작업 디렉터리 | 값 (3.1). `cd`, `pushd`, `popd`로 바뀐다. 초기값은 역할이 정한다 (빌드는 `$srcdir`, 훅은 `/`) |
| 셸 옵션 | `set -e`, `shopt` 등 |
| 마지막 종료 상태 | `$?`. 보통 unknown |
| 종료 여부 | `exit`/`return`/`set -e`로 이 경로가 끝났는가 |

서브셸(`( ... )`, 파이프라인의 각 단계, `$(...)`, `&`)은 상태의 **복사본**으로 걷고 끝나면 버린다. 밖에는 효과(단계)만 나온다.

## 4. 단계의 확정도

순회가 내보내는 모든 단계에 확정도를 붙인다.

| 확정도 | 뜻 |
|---|---|
| `definite` | 이 시간선에서 이 경로를 지나면 반드시 실행된다 |
| `conditional` | 분기 조건 때문에 실행될 수도 있다. 조건을 단계에 붙인다 |
| `unknown` | 무엇을 실행하는지 모른다. 모든 동작 × 모든 위치로 취급한다 |

## 5. 설계 원칙

1. **may 분석**: 확실하지 않으면 "할 수 있다"로 둔다. 놓침은 모델링하지 않은 동적 기능에서만 생긴다.
2. **미상은 최악**: `unknown`은 9칸 전부에 속한다. 역할이 `unknown`이면 모든 역할로 보는 것과 같은 원칙이다.
3. **실행하지 않는다**: 난독화 해독을 포함해 전부 정적이다. 분석 중에 파일을 만들거나 명령을 돌리지 않는다.
4. **침묵은 판정이 아니다**: 걷지 않은 것, 풀지 못한 것, 중단한 것은 모두 보고서에 적는다 (11절).
5. **종료를 보장한다**: 모든 반복, 인라인, 경로에 상한이 있다 (12절). 입력이 악의적일 수 있다.

## 6. 분기

### 6.1 조건 평가

조건을 직접 평가하는 형태는 아래로 **제한**한다. 나머지는 모두 "모름"이다.

- `true`, `false`, `:`
- `[ ]`, `[[ ]]`, `test` 중 리터럴 또는 known 변수끼리의 문자열 비교(`=`, `!=`), `-z`, `-n`, 정수 비교, `!`, `&&`, `||`
- 평가 불가: 명령을 실행해야 아는 조건(`grep -q`, `test -f`), unknown/set 값에 의존하는 조건, 환경 변수(`CARCH`, `date`, `hostname`)

### 6.2 경로

- 조건이 **항상 참 또는 항상 거짓**으로 풀리면 그 경로 하나만 따라간다. 따라가지 않은 쪽은 걷지 않지만 **걷지 않았다는 사실을 기록**한다 (`skipped-branch`, 줄 범위).
- 모르면 **실제로 갈라서** 양쪽을 따로 걷는다. 각 경로는 상태의 복사본이다.
- `&&`, `||`는 분기다 (`test -f x && rm x`의 `rm`은 conditional). `case`는 패턴마다 분기하고, 값이 known이면 맞는 하나만 간다.

### 6.3 합류

분기 구문(`if`, `case`, `&&`/`||`)이 끝나는 지점에서 경로를 **합친다**.

- 변수: 값 합류 (3.1).
- 작업 디렉터리, 셸 옵션, 함수/alias 정의: 같으면 유지, 다르면 합집합 또는 unknown.
- 한쪽 경로가 `exit`로 끝났으면 그 경로는 합류에서 뺀다.
- 효과(단계)는 합치지 않고 모두 남긴다. 각 단계에 분기 조건을 붙인다.

경로 수는 `PATH_MAX`(초안 64)를 넘지 않는다. 넘으면 가까운 합류 지점을 앞당겨 합치고 **"분석 간소화"**를 알린다.

### 6.4 환경 조건부 실행 (알림 후보)

조건이 환경 탐침(`date`, `hostname`, `whoami`, `uname`, `CARCH`)에 의존하고 그 가지에 위험한 칸의 단계가 있으면 알림을 낸다.
예: `if [ "$(date +%s)" -gt 1700000000 ]; then curl ... | sh; fi`. 특정 시점이나 대상에서만 터지는 악성 코드의 전형이다.
(시스템 읽기 → 조건 → 실행) 형태다.

## 7. 반복문

`for`, `while`, `until`, C식 `for`, `select`.

1. **횟수를 알 때만 펼친다**: `for x in a b c`처럼 목록이 리터럴/known이고 `UNROLL_MAX`(초안 20) 이하일 때. 반복 변수는 매 바퀴 known이다.
2. **횟수를 모르면 본문을 한 번 걷는다** (확정도 `conditional`, `repeat` 표시):
   - 본문에서 대입되는 변수는 반복 뒤 **unknown**으로 만든다. 첫 바퀴와 다음 바퀴의 값이 다르기 때문이다.
   - 본문에서 `cd`/`pushd`/`popd`가 있으면 작업 디렉터리를 unknown으로 만든다.
   - 반복 변수가 unknown이어도 아는 정보는 남긴다 (`*.txt` → 빌드트리 안의 경로).
3. `while true`, `until false`처럼 종료 조건이 없는 반복은 본문을 한 번 걷고 "종료 조건 없음"을 알린다.
4. `break`, `continue`는 그 바퀴의 나머지를 건너뛴다. 합류에서는 둘 다 가능한 경우로 합친다.
5. **후속 개선**: 한 번 걷기 대신 **고정점 반복**(상태가 더 안 바뀔 때까지 반복, `FIX_MAX` 번 안에 수렴하지 않으면 확대해서 unknown). 영역이 작아서 보통 2~3번 안에 수렴한다. 먼저 1~4로 시작하고 개선은 그다음에 한다.

## 8. 함수

### 8.1 호출

호출 지점에서 함수 본문을 **인라인**해서 같은 순회로 걷는다.

- 인자: `$1`, `$@`, `$#`를 호출 인자의 값(3.1)으로 바인딩한다. `local`은 호출 범위에서만 유효하다.
- 호출 지점마다 역할이 정확히 정해진다 (호출한 쪽의 역할). 지금 `roles.py`의 합집합은 이 정확한 값의 근사다.
- 각 단계는 **원래 줄 번호**와 **호출 경로**(어느 함수가 어느 줄에서 불렀는가)를 보존한다. 같은 원래 줄의 같은 발견은 하나로 합친다.
- 함수가 파이프라인이나 `( )` 안에서 호출되면 서브셸이다 (3.2).

### 8.2 호출되지 않는 함수

어디에서도 도달하지 못한 함수는 **알림을 내고** 본문도 한 번 분석한다. 역할은 `unknown`(모든 역할)이다.
`eval`, `trap` 문자열, `export -f`로 간접 호출될 수 있으므로 알림만 내고 버리면 숨겨진 코드를 놓친다.
(`unreachable-function`, 수준 `expected`.)

### 8.3 재귀

호출 그래프의 강연결 성분(자기 호출, 상호 재귀)에 속한 함수는 **인라인에서 제외**한다. 대신:

- 본문을 **한 번 분석**한다 (재귀 호출 지점은 "재귀 호출"로 표시하고 더 따라가지 않는다).
- 호출 지점에는 그 본문의 효과를 `conditional`로 붙이고 "재귀 호출, 실행될 수 있음"을 알린다.

인라인 제외를 분석 제외로 해석하지 않는다. 재귀 뒤에 코드를 숨길 수 있기 때문이다.

### 8.4 인라인 예산

인라인한 단계의 총수가 `INLINE_MAX`(초안 5000)를 넘으면 그 이후의 호출은 인라인하지 않고 **요약**(호출되는 함수의 효과 합집합, 확정도 `conditional`)을 붙인다. "분석 간소화"를 알린다. 분석을 끝까지 하되 정확도만 낮춘다.

## 9. 종료 의미와 동적 코드

### 9.1 종료

- `exit`는 이 시간선의 모든 경로를 끝낸다 (서브셸 안이면 그 서브셸만). `return`은 함수를 끝낸다.
- `set -e`가 켜진 상태에서 실패할 수 있는 명령 뒤는 `conditional`이다 (명령의 종료 상태는 보통 모른다).
- `trap ... EXIT/ERR`의 본문은 종료 지점에서 걷는다. `trap ... DEBUG`는 모든 명령 앞에서 걷는다는 의미라서 **미상으로 덮고 알린다**.
- `exit` 뒤의 코드는 걷지 않지만 `skipped-branch`로 기록한다.

### 9.2 동적 코드

| 구문 | 처리 |
|---|---|
| `eval "$s"`, `sh -c "$s"` | `s`가 known/set이면 그 문자열을 다시 파싱해 순회에 넣는다 (재파싱 깊이 `REPARSE_MAX`, 초안 4). 아니면 unknown + 알림 |
| `source file`, `. file` | 저장소 안의 파일이면 그 파일을 순회에 넣는다. 아니면 unknown + 알림 (`$srcdir`의 다운로드 파일은 알 수 없다) |
| 변수로 만든 명령 이름 | 값이 known/set이면 풀고, 아니면 unknown + 알림 |
| `alias` | `expand_aliases`가 켜졌고 정의가 확실하면 풀고, 확실하지 않으면 그 이후의 명령 이름을 unknown으로 두고 알림 |
| 함수로 가린 명령 (`curl() { ...; }`) | 함수가 우선한다. `command`, `builtin`, `\cmd`로 건너뛰는 경우도 따른다 |
| `PATH` 변경 | 이후의 명령 이름 해석이 unknown. 알림 |
| `LD_PRELOAD`, `LD_LIBRARY_PATH`, `BASH_ENV`, `ENV`, `command_not_found_handle`, `enable`, `hash -p` | 명령을 바꿀 수 있는 행동으로 분류해 알림 (모델링 범위는 열린 질문) |

## 10. 난독화

순회 중에 아래를 발견하면 **무조건 `warning`으로 알린다.** 풀었든 못 풀었든, 풀린 내용이 무해해 보이든 마찬가지다.
난독화 자체가 이 도구의 의심 신호이고, 정상 PKGBUILD가 코드를 숨길 이유는 거의 없기 때문이다.

- 대상: 따옴표 쪼개기(`c''url`), 변수로 조립한 명령 이름, base64/hex/rot13/`xxd -r`, `${IFS}`, `eval` 문자열, 문자열 슬라이스 조립, 8진/16진 이스케이프.
- **풀었음**: 풀어낸 내용을 보고서에 보여 주고, 풀린 코드는 일반 코드처럼 순회한다. 풀린 코드가 더 높은 수준의 발견을 내면 그 수준이 우선이다. 난독화 사실 자체의 수준은 내려가지 않는다 (`warning`).
- **풀지 못했음**: unknown으로 덮고 `warning`. 풀지 못한 이유를 적는다.
- 같은 줄에서 다른 경고와 겹치면 경고가 둘 다 남는다 (난독화 경고는 정보 수준 발견을 가리지 않고, 정보 수준 발견이 난독화 경고를 가리지도 않는다).
- 풀기는 정적이다. 디코딩 결과 크기 상한(초안 1 MiB)과 재파싱 깊이 상한 (`REPARSE_MAX`)이 있다.
- 정상 PKGBUILD에서의 빈도는 코퍼스 `measure`로 미리 재서 경고가 너무 잦지 않은지 확인한다. 잦다면 난독화의 **정의**를 좁히는 것이지 수준을 낮추는 것이 아니다.

지금 코드에서 이미 `warning`인 규칙: `obfuscated-command-name`, `base64-exec`, `decode-exec`, `network-pipe-shell`.
이 정책에 따라 `warning`으로 올린 규칙: `hex-escapes`, `ifs-evasion`, `rot13`, `substring-obfuscation`.
아직 `info`로 남은, 난독화와 겹칠 수 있는 규칙(범위를 정해야 함): `eval`(약한 신호), `base64-decode`(데이터 복호화일 수 있음), `dynamic-command`(명령 이름이 변수로 만들어짐).

## 11. 출력

### 11.1 단계 기록

순회는 단계마다 다음을 낸다 (`docs/IR.md`의 단계를 확장한다).

| 필드 | 내용 |
|---|---|
| `file`, `lines` | 원래 줄 범위 |
| `call_chain` | 인라인 호출 경로 |
| `timeline` | `parse` / `build` / `package` / `hook` (+ 훅 이름, 분할 패키지 이름) |
| `role` | 호출 지점에서 정해진 역할 |
| `certainty` | `definite` / `conditional` / `unknown` |
| `condition` | 분기 조건 (conditional일 때) |
| `repeat` | 반복 안에서 걸었는가 |
| `command` | 해석된 명령과 인자 (값 영역 포함) |
| `table_entry` | 사용한 표 항목 |
| `cells` | 칸과 하위 분류 태그의 집합 |
| `expected_actions` | 사람이 읽는 예상 행동 ("`/etc/foo`에 쓴다", "`https://x`에서 받는다") |

### 11.2 분석하지 못한 것 (커버리지)

보고서는 반드시 아래를 따로 적는다.

- 파싱하지 못한 줄과 분석하지 않은 파일
- `unknown`으로 덮은 단계와 그 이유 (동적 명령, 풀지 못한 난독화, `eval`, `source`)
- 걷지 않은 분기 (`skipped-branch`)와 호출되지 않은 함수
- 분석 간소화 (경로 상한, 인라인 예산, 반복 상한, 재파싱 상한에 걸린 곳)

"문제 없음"과 "분석하지 못함"을 구분해서 보여 주는 것이 목적이다.

## 12. 예산과 종료 보장

| 이름 | 초안 값 | 넘으면 |
|---|---|---|
| `SET_MAX` | 8 | 집합을 unknown으로 |
| `UNROLL_MAX` | 20 | 펼치지 않고 한 번 걷기 |
| `PATH_MAX` | 64 | 경로를 합치고 "분석 간소화" |
| `INLINE_MAX` | 5000 단계 | 이후 호출은 요약으로 |
| `REPARSE_MAX` | 4 | unknown + 알림 |
| `FIX_MAX` | 8 (고정점 도입 시) | 확대해서 unknown |
| 디코딩 크기 | 1 MiB | 풀지 않고 unknown |
| 전체 시간 | 파일당 상한 (초안 10 s) | 분석 중단, 사용자 결정은 N으로 닫힘 |

상한에 걸리면 항상 보고서에 적는다. 분석이 충돌하거나 시간을 넘기면 "정상"이라고 말하지 않고 안전 쪽으로 닫는다.

## 13. 지금 코드와 구현 순서

- 1단계 구문 분석은 이미 있다 (`shast`, `astadapt`, `parsed`). 안정 변수 치환(`stable_variables`)은 값 영역의 known 부분의 초기형이다.
- `roles.py`의 역할 합집합은 인라인 예산 초과 때의 요약과 같은 근사다. 순회가 생기면 호출 지점별 정확한 역할로 대체된다.
- `ir.py`의 단계와 단위, `commandtable.py`의 효과는 11.1의 단계 기록으로 이어진다.

구현 순서 제안 (각 단계가 끝나면 차이 검사로 기존 결과가 같은지 확인한다):

1. 값 영역과 상태, 단순 명령의 순회 (분기와 반복 없이 직선 코드). 기존 `steps`와 같은 단계가 나오는지 확인
2. 상수 조건 평가와 분기, 합류, 경로 상한
3. 함수 인라인, 호출되지 않은 함수 알림, 재귀 처리, 인라인 예산
4. 반복문 (펼치기 + 한 번 걷기)
5. 동적 코드 (`eval`, `source`, alias, `PATH`)와 난독화 풀기, 재파싱
6. 시간선별 순회 (진입점 순서, 분할 패키지, `.install`)
7. 단계 기록 필드와 커버리지 보고
8. 고정점 반복, 문자열 영역 확장

## 14. 열린 질문

- 시간선: 진입점 순서(`pkgver → prepare → build → check → package`)와 분할 패키지, `.install` 훅, pacman `.hook` 파일을 어떻게 순회에 얹을 것인가
- PKGBUILD 외 입력(패치, 보조 스크립트, `source`/체크섬 배열, 이전 버전 차이)의 처리 범위
- 명령을 바꾸는 행동(`PATH`, `trap`, `BASH_ENV`, `LD_PRELOAD`, `enable`, `command_not_found_handle`, `hash -p`)을 어디까지 모델링하고 어디부터 unknown으로 덮을 것인가
- 데이터 흐름 단계(3단계)의 상세: 파이프, 리다이렉션, 임시 파일, 환경 변수를 순회 안에서 할지 뒤에서 할지
- 난독화 정의의 범위: `eval`, `base64-decode`, `dynamic-command`를 난독화로 보아 `warning`으로 올릴 것인가 (정책은 "난독화는 무조건 `warning`"으로 확정, 코퍼스 측정 후 정의를 조정)
- 사용자 결정 단계: 종료 코드, JSON 출력, 프롬프트의 출력 위치(tty), 비대화형 실행
- 칸 분류(9칸과 하위 분류)와 이 문서의 단계 기록을 어떻게 이을 것인가 (`cells` 필드의 형식)
- 숫자 상한들의 최종 값 (`measure`로 정함)
